# 00 — Overview

## 1. მიზანი

ონლაინ მაღაზია, სადაც კომპანია ყიდის **მხოლოდ საკუთარ პროდუქციას**: ელექტრომობილის დამტენების სათადარიგო ნაწილებს, კაბელებს, კონექტორებს, აქსესუარებს და ა.შ.

მაღაზიის მთავარი ფუნქცია **თავსებადობის ფილტრია**. მომხმარებელი ირჩევს თავის დამტენს (ბრენდი → მოდელი) და ხედავს მხოლოდ იმ ნაწილებს, რომლებიც ამ მოდელს ერგება. ამისთვის მას კონექტორის ტიპის ან ტექნიკური მახასიათებლების ცოდნა არ სჭირდება.

## 2. Scope

პროექტის ფარგლები: რა შედის პირველ ვერსიაში (MVP) და რა დაემატება მოგვიანებით.

### პირველ ვერსიაში (MVP) შედის
- პროდუქტების კატალოგი კატეგორიებით, ძებნით და ფილტრებით
- თავსებადობის ფილტრი (დამტენის ბრენდი → მოდელი)
- ორი ენა: ქართული (ნაგულისხმევი) და ინგლისური
- ვალუტა: მხოლოდ **GEL**
- რეგისტრაცია / ავტორიზაცია არსებული **Identity** სერვისით (OAuth2 / OIDC)
- კალათა, checkout, ონლაინ გადახდა **TBC / BOG** ბარათით (**Billing** სერვისი)
- ფისკალური ჩეკი RS.ge-ზე (**Fiscal** სერვისი)
- მომხმარებლის კაბინეტი: შეკვეთები, მისამართები, პროფილი
- Admin panel: პროდუქტები, კატეგორიები, თავსებადობა, მარაგი, შეკვეთები, მომხმარებლები, live dashboard
- მიღება: **ოფისიდან გატანა** და/ან **მიწოდება, რომელსაც ადმინი ხელით მართავს** (კურიერულ სერვისთან ინტეგრაციის გარეშე)

:::question id="biz-fulfillment" to="ბიზნესი"
მიღების რომელი მეთოდები გვინდა MVP-ში: მხოლოდ **ოფისიდან გატანა**, თუ **ხელით მართული მიწოდებაც**? თუ მიწოდებაც, რა ღირს (ფიქსირებული / ქალაქის მიხედვით / უფასო X ₾-დან)? გატანის მისამართი და სამუშაო საათები?
:::


### პირველ ვერსიაში არ შედის (მოგვიანებით)
- B2B / კომპანიები (სპეციალური ფასები, ინვოისით გადახდა). **სქემა ისეა აგებული, რომ მოგვიანებით დაემატოს**
- კურიერულ კომპანიებთან ინტეგრაცია
- მობილური აპი და push შეტყობინებები
- რამდენიმე საწყობი
- ERP / ბუღალტრულ პროგრამასთან სინქრონიზაცია
- პრომო-კოდები, ფასდაკლების წესები, ლოიალობა
- შეფასებები და კომენტარები

## 3. მომხმარებლები და როლები

| როლი | ვინ არის | სად მუშაობს |
|---|---|---|
| Guest | არაავტორიზებული ვიზიტორი | Storefront: ათვალიერებს, ამატებს პროდუქტს კალათაში |
| Customer (Individual) | რეგისტრირებული ფიზიკური პირი | Storefront: ყიდულობს, ხედავს შეკვეთებს |
| Customer (Business) | კომპანია — **მოგვიანებით** | — |
| Admin | სრული წვდომა | Admin panel |
| Manager | შეკვეთების მართვა | Admin panel |
| Content Editor | კატალოგი და თავსებადობა | Admin panel |
| Warehouse | მარაგი და შეკვეთების მომზადება | Admin panel |

დეტალური უფლებები: [08-admin-panel.md](08-admin-panel.md#3-როლები-და-უფლებები).

## 4. ძირითადი სცენარები

1. მომხმარებელი ირჩევს „ჩემი დამტენი: ბრენდი X, მოდელი Y“ და ხედავს მხოლოდ თავსებად ნაწილებს.
2. მომხმარებელი ეძებს ნაწილს სახელით, SKU-ით ან ქარხნული (OEM) ნომრით.
3. მომხმარებელი ამატებს ნაწილს კალათაში, გადის checkout-ს, იხდის TBC/BOG-ით და იღებს დადასტურებას.
4. გადახდის შემდეგ ავტომატურად გამოიწერება ფისკალური ჩეკი.
5. ადმინი live რეჟიმში ხედავს ახალ შეკვეთას, ამზადებს და ცვლის სტატუსს.
6. ადმინი ამატებს პროდუქტს, ტვირთავს ფოტოებს და უთითებს, რომელ მოდელებს ერგება.
7. ადმინი აფორმებს მარაგის მიღებას (stock receipt) ან მის კორექტირებას (adjustment). ყველა ცვლილება ინახება ისტორიაში.
8. ადმინი აუქმებს გადახდილ შეკვეთას: refund ხდება Billing-ით, დაბრუნების ჩეკი კი Fiscal-ით.

## 5. არაფუნქციური მოთხოვნები

| თემა | მოთხოვნა |
|---|---|
| ენები | ka (default), en. URL: `/ka/...`, `/en/...` |
| ვალუტა | GEL. ფასები ინახება **თეთრებში (integer)** |
| დღგ | ფასები მოიცავს დღგ-ს (18%), იხ. კითხვა ქვემოთ |
| Mobile | Mobile-first დიზაინი |
| სიჩქარე | პროდუქტის გვერდი: LCP < 2.5s; API p95 < 300ms (კატალოგი) |
| SEO | SSR/ISR, sitemap, hreflang, Product JSON-LD |
| საიმედოობა | გადახდილი შეკვეთა და ჩეკი არ უნდა დაიკარგოს, თუნდაც რომელიმე სერვისი დროებით გაითიშოს |
| მარაგი | ბოლო ერთეული ორ სხვადასხვა მყიდველს არ უნდა მიეყიდოს |
| აუდიტი | Admin-ის ყველა ცვლილება იწერება audit log-ში |

## 6. ტერმინები

| ტერმინი | მნიშვნელობა |
|---|---|
| SKU | პროდუქტის უნიკალური შიდა კოდი |
| OEM ნომერი | მწარმოებლის ქარხნული ნაწილის ნომერი |
| Charger model | დამტენის მოდელი, რომელსაც ნაწილი შეიძლება ერგებოდეს |

| Reservation | მარაგის დროებითი დაკავება checkout-ისას, სანამ გადახდა დასრულდება |
| Outbox | ბაზის ცხრილი, საიდანაც ივენთები საიმედოდ იგზავნება NATS-ში |
| BFF | Backend-for-Frontend. Next.js-ის სერვერული ნაწილი, რომელიც ტოკენებს ინახავს |
| SSE | Server-Sent Events, სერვერიდან ბრაუზერისკენ ცალმხრივი live ნაკადი |
| Minor units / თეთრი | 1 GEL = 100 თეთრი; ყველა თანხა ინახება მთელ რიცხვად |
